Одна й та сама плата **YD_F102_MIPI_V3.0** (Allwinner F102, Melis RTOS, DDR3 128 МБ, SPI NOR 8 МБ XM25QH64C, тач GSL1680), але **різні LCD-панелі**. Прошивка однакова (інтерфейс, мови, ресурси), відрізняється лише ініціалізація панелі в ядрі. Образ однієї рамки **не можна шити в другу**.

## Як збирати версії для двох рамок
1. **Інтерфейс (спільний для обох).** Збирається на Mac (`tools/build_image.py`, правки `patches/…`, описи в `docs/BUILD_IMAGE_UK.md`). Результат має заводське ядро й конфіг.
2. **Профіль рамки** (Windows або Mac, `build_kit/`):
   ```
   python tools\make_variant.py --frame 1 --name <версія> --base <образ інтерфейсу>
   python tools\make_variant.py --frame 2 --name <версія> --base <образ інтерфейсу>
   ```
   Вихід: `out\F1_<версія>\` і `out\F2_<версія>\` з `smartframe.img`, `SHA256SUMS`, `manifest.json`, `verify.txt`. База має бути з **заводським ядром і конфігом**; інакше інструмент відмовляє. Профілі зберігаються в `build_kit/data/frames.json` (джерело: `tools/frames.json`).
3. Перед записом перевірити SHA-256, прошити тільки відповідну рамку. Прошивку виконує власник.
4. Експерименти з панеллю (без `--frame`) тільки на рамці 2 і лише за окремим рішенням: див. `make_variant.py --help`.

## Чим відрізняються образи (екран)
Лише кодом ініціалізації панелі для ID `98 81 1C` (одна ділянка ядра, 3766 байтів); таймінг, DSI, конфіг, інтерфейс однакові. Заводська таблиця проти K101: 101 із 180 спільних регістрів різні (GIP, живлення, гама). Повний розбір: [FRAMES_SCREEN_DIFF.md](FRAMES_SCREEN_DIFF.md), перелік: `analysis/frame-screen-diff-20261116/`.

## Рамка 1: що знаємо
- Працює на заводському ядрі, отже її панель відповідає на ініціалізацію, яку робить заводська гілка автовизначення. ID панелі й потреба в UART-журналі: **не знято**.
- Золота прошивка v11k: світла тема «жорстка тінь», українська мова, власна заставка, плитки 208×192, кільце вибору `#7B1E3F`, виправлені календар/будильник/годинник. Детально: `PROJECT_STATE.md` (розділи v11–v11k) і пам'ять проєкту.
- Не прийнято: v11l (чорні екрани → білі).
- Відкрите: повільні мініатюри фото (код мініатюр заводський; причина не встановлена).

## Рамка 2: що знаємо
**Робочий рецепт (перевірено на пристрої):** база v11k, таблиця `linux_k101_im2byl02_init` (з Linux `panel-ilitek-ili9881c.c`) у гілці ID `98 81 1C`, автовизначення збережене, **заводський таймінг** `dclk 73, ht 890, hbp 25, hspw 20, vt 1340, vbp 20, vspw 4` (61,21 Гц; hfp 65, vfp 40). Команда: `make_variant.py --table linux_k101_im2byl02_init --timing 73,890,25,20,1340,20,4`. Побайтово відтворено на Mac (SHA збігається з образом, зібраним на Windows).

**Історія і справжня причина.** Усі образи зі зміненим таймінгом (12–14 від 04.11 і v12c) були збудовані нашим інструментом, який записував поля таймінгу в хибному порядку (ядро читає `hbp, vbp, hspw, vspw`; помилку знайдено 16.11 за журналом UART). Тому, зокрема, таблиця K101 у переборі 04.11 (образ 13) потрапила в ядро з таймінгом `dclk 70, hbp 56, vbp 8, hspw 21, vspw 6`, який ядро відхиляє (`vbp − vspw ≤ 3`, «vbp is too small»), і дала смуги. Висновок 04.11 «жодна таблиця ILI9881 не підходить» був хибним: правильна таблиця вже була в корпусі. Додатково ми довго перебирали чужі таблиці (JieLi дала «живу, але розсинхронізовану» картинку, JD-драйвери чорний екран) і режим DSI (`lcd_dsi_if=2` ламає видачу кадрів: десятки `timeout`; правильне 0).

| Твердження | Статус |
|---|---|
| Рецепт K101 + заводський таймінг дає ідеальну картинку | **перевірено** на пристрої, образ відтворюється |
| Образи 12–14 від 04.11 провалились через наш хибний таймінг | **перевірено** (прочитано поля таймінгу їхніх ядер) |
| Правило `hbp > hspw` (у sunxi `hbp` включає sync) | узгоджене з усіма 9 панелями реєстру ядра й зі sunxi; зависання при порушенні **повідомлено, але не перевірено нами**; інструмент відмовляє |
| Заводська таблиця `inx_f101a35` не підходить склу (GIP, сторінки 3/4) | правдоподібно, **не перевірено** (дампа регістрів не знімали) |
| Скло рамки 2 «того самого виробника, що рамка 1» | припущення; доказів немає |
| «PLL стабільний лише на 73 МГц, 68 МГц зависає» | **не підтверджено**: образи з 72, 70 і 68 МГц завантажувались (журнали/нотатки). 73 лишаємо як заводське значення |

**Не повторювати:** `--set lcd_dsi_if=2`, таймінг із `hbp ≤ hspw` або `vbp − vspw ≤ 3`, таблиці JieLi/Seeed/інші без потреби, примусове `--no-keep-detect`.

## Корисні факти про залізо (обидві рамки)
- Вхід у режим прошивання: вимкнена рамка, USB-кабель у ПК, **затиснути Power**, вставити в USB-A порт рамки (PhoenixSuit, режим `全盘擦除升级`). Працює завжди, навіть при чорному екрані.
- UART2 (журнал): площадки `PE6 TX2`, `PE7 RX2`, `GND`, 115200 8N1, 3,3 В. Для журналу достатньо GND + RX адаптера на `PE6 TX2`.
- Ядро й конфіг: адреси й структури в `PROJECT_STATE.md`; таблиця таймінгу `auto_mipi` у розпакованому ядрі за зсувом `0x10E7F0` (9×u16: `dclk, x, y, ht, vt, hbp, vbp, hspw, vspw`); слот ініціалізації ILI9881 `0x810AE…0x81F93`; запас слоту ядра менше 1 КБ.

## Відкрите
1. **Зняти UART-журнал рамки 1** (нічого не прошиваючи): ID панелі (`mipi id read ok`) і flash. Якщо ID рамки 1 теж `98 81 1C`, то заводська гілка її обслуговує, а патч рамки 2 їй шкодить; якщо ID інший, обидва профілі можна об'єднати в один образ. Поки що тримати два окремі образи.
2. Повільні мініатюри на рамці 1 (і, ймовірно, на обох).
3. Для рамки 2 новий UI ще не збирався з профілем: перший такий образ перевірити на пристрої.
